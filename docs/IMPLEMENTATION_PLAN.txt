一、产品目标与默认假设
用自然语言创建 Android 原生桌面小组件，支持预览、连续对话修改、撤销、保存和添加桌面。
代表需求：“做一个深色小组件，显示上海天气和本周六考试的倒计时。”
默认以中文体验为主、Android 12+、单人本地使用优先；项目名为暂定工作名称。
首版只生成受约束的组件配置，不执行模型生成的任意代码，不以完整兼容 Scriptable 为目标。
无需替换用户桌面启动器。模型只在生成和修改时调用，普通数据刷新不调用模型。

二、MVP 范围
1. 组件库：创建、复制、重命名、删除、JSON 导入导出。
2. 对话创建：输入需求、生成预览、继续修改、失败提示、撤销到上一版本。
3. 基础节点：Row、Column、Box、Text、Image、Spacer、Progress、Action；支持颜色、内边距、字号、对齐和圆角。
4. 数据源：本地文字、日期、倒计时、电量；天气作为第一个外部数据适配器。
5. 桌面组件：多实例独立绑定配置，支持常见尺寸、尺寸变化、手动刷新、点击打开 App 或 URL。
6. 模型设置：首先接入一个支持结构化输出的服务，保留供应商适配接口；开发版使用用户自己的密钥，不内置共享密钥。
7. 日历和自定义 HTTP 数据源列为 MVP 后扩展，避免权限和鉴权阻塞主流程。
暂不包含：脚本市场、账号云同步、任意 JS、完整 Scriptable 兼容、复杂动画、后台秒级执行。

三、架构与技术路线
Android：Kotlin + Jetpack Compose；应用内导航、对话、组件库和设置采用原生界面。
配置：kotlinx.serialization + 版本化 WidgetSpec；第一阶段定义 JSON Schema、节点上限、深度上限和可用属性。
存储：Room 保存组件、版本和桌面实例映射；DataStore 保存非敏感设置。
密钥：使用 Android Keystore 管理加密密钥，对模型凭证加密存储；日志、导出和模型上下文剔除凭证。
联网：统一 HTTP 客户端，分别封装模型服务与业务数据源；配置超时、取消和有限重试。
桌面：优先验证 Glance/RemoteViews 渲染基础节点，复杂视觉以后增加 Canvas 位图节点。
预览：共享 WidgetSpec、布局约束和数据快照，应用内预览与桌面使用不同适配器；不能假定 Compose 预览天然等同于桌面结果。
调度：WorkManager + 手动/事件触发；周期任务最小 15 分钟，可能因系统节电延迟，不承诺精确刷新。
工程先采用单 app 模块，按 model / ai / data / render / widget / ui 分包；规模增长后再拆 Gradle 模块。

数据流：
用户需求 + 当前 WidgetSpec + 可用能力列表
  → 模型返回候选完整 WidgetSpec
  → 结构、语义、资源预算校验
  → 绑定数据并预览
  → 用户保存为新版本
  → 对应桌面实例更新
非法配置最多自动修复两次，失败保留上一个有效版本。首版返回完整配置，暂不实现易出错的任意 JSON Patch。

四、阶段计划与验收
时间为一名熟悉 Android 开发者的投入估算，按依赖推进，不代表固定上线承诺。

P0：技术验证与范围冻结（3–5 个工作日）
任务：检查本机 JDK/SDK；建立 Android 工程；手写三份 WidgetSpec；验证嵌套布局、点击、缩放与多实例。
产出：可安装 debug APK、配置协议草案、真实桌面截图、渲染技术决策记录。
验收：至少两个启动器上可添加组件；两个实例修改互不影响；重启进程后恢复；决定 Glance 是否满足布局范围。
这是第一道关口：确认桌面闭环可行后再投入 AI 和界面完善。

P1：配置引擎与持久化（1–2 周）
任务：实现配置校验、基础节点渲染、数据绑定、版本记录、预览、实例映射和导入导出。
产出：无需模型即可运行的组件编辑与桌面应用闭环。
验收：文字、电量、倒计时三种组件可用；无效、过深和过大的输入被拒绝；升级配置有迁移路径。

P2：AI 对话生成（1–2 周）
任务：模型适配器、结构化提示词、候选预览、多轮修改、取消、有限修复与回滚。
产出：自然语言创建和修改的主流程。
验收：固定至少 20 条中文需求，首次有效配置目标 ≥80%，两次修复内目标 ≥95%；统计有效率与实际满足需求分别评分；修复失败不覆盖有效组件。
测试集覆盖“只改背景”“只增大温度”“保留布局换城市”等增量指令；记录模型、版本和测试日期。

P3：动态数据和刷新（1–2 周）
任务：选定天气服务并核对许可、配额与国内连通性；加入缓存、过期状态、手动刷新和后台调度。
产出：真实天气与本地数据的组合组件。
验收：断网、超时、无密钥和额度不足有可理解提示；旧数据附更新时间；后台只请求业务接口；同源数据共享缓存。

P4：可用性与设备验证（1–2 周）
任务：中文界面、首次引导、权限按需申请、错误诊断、窄尺寸和大字体适配。
产出：可日常试用 APK、操作说明、已知限制和测试记录。
验收：真实设备完成创建→修改→添加→缩放→刷新→重启恢复；覆盖至少 Pixel/AOSP 与一个国内厂商系统；检查多个实例、Doze 和进程被回收后的行为。
缺少对应真机时明确记录未验证项，不将模拟器结果视为真机结论。

预计：技术演示 2–3 周；可日常试用 MVP 约 6–10 周。数据源接入与设备适配可能延长工期。

五、验证策略
单元测试：协议校验、版本迁移、数据绑定、时间/时区、缓存和实例映射。
模型评测：固定中文需求及多轮修改集；不把远程模型调用放进普通单元测试。
集成测试：模拟服务验证非法模型输出、取消、断网、超时和限流；校验凭证不进入日志与导出。
设备验证：预览与桌面逐项比较；不同尺寸、系统字体、启动器、重启和后台节电场景。
发布前运行编译、相关单元测试与 Android lint；保存可复现的构建步骤。

六、后续演进
V0.2：日历、自定义 HTTPS JSON 数据源、字段映射、更多图表与 Canvas 渲染。
V0.3：受控 JS 扩展，仅在明确执行预算、权限模型和隔离方式后引入。
V0.4：选择一批真实 Scriptable 脚本建立兼容清单，按需求实现兼容 API。
商业化阶段再建设后端模型代理、用户鉴权、配额与计费；客户端不分发公共服务密钥。

七、主要风险与处理
渲染限制：P0 先验证，第一版限制能力集合，复杂视觉使用后续位图节点。
模型幻觉：只暴露已实现的数据源和属性，确定性校验后才能保存和执行动作。
刷新延迟：显示更新时间与缓存状态，允许用户手动刷新。
外部数据：服务商选择、费用、许可和国内可用性在接入前核实。
隐私：只发送完成任务所需的配置和请求，默认不向模型发送日历正文、联系人和凭证。
范围扩张：Scriptable 兼容、任意脚本和云市场均排在原生组件闭环之后。
